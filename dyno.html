Dyno

Measures AI agents step by step, and blocks changes that make them worse.

AI agents are non-deterministic: the same question can pass once and fail the next time. Unit tests with scripted models cannot see behaviour changes, and judging only the final answer hides wasted steps, wrong tool use and invented facts. Dyno is built to see all of that.

What it does

01

Dyno runs any agent on a suite of test cases several times each, records every step (model calls, tool calls, results), scores each attempt, compares runs, groups failures into clusters, and fails a pull request when the agent gets worse.

How an evaluation runs

02
DefineTest cases in YAML

Expected key points, tools that must or must not be called, step limits and tags. Agents plug in in-process or over HTTP.

RunRepeated attempts

Each case runs several times, with every step recorded.

ScoreScorers

Deterministic checks plus LLM judges.

Tool use, steps, costTask success judgeHallucination judgeQuality judge
AnalyseCompare and cluster

pass@k and pass^k, flaky cases, run-to-run comparison, failure clustering with embeddings and k-means.

GateCI regression gate

A reusable GitHub Action runs the agent on the PR and the base branch, and blocks the merge if quality drops.

Can the judges be trusted?

03

Before any judge was used, I labelled answers by hand, blind to the judges, and measured agreement as Cohen's kappa.

JudgeAgreement with human labels
Task rubricκ = 1.00
Qualityκ = 0.95
Hallucinationκ = 0.63

The hallucination judge is the weakest of the three, so its scores are read with more caution.

What it found

04
FindingEvidence
Found Scout's biggest weakness and measured the fixReports stopped at "the sources don't say" instead of searching further. After the fix: task success 47% → 80%, cases right every time 4/10 → 7/10, none got worse
Blocked a bad change that passed every unit testA "cost cut" PR dropped task success from 80% to 40%, and actually cost 26% more per question
Showed that one run is not enoughSame code: pass@3 60% but pass^3 40%; one run scored 70%, another 47%

Why this matters

05

The same code scored 70% on one run and 47% on another. Without repeated runs and pass^k, a team would ship or reject changes based on noise.
